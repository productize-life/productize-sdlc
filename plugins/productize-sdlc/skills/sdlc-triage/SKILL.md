# Triage (tracker-first)

Move issues on your tracker through a small state machine of triage roles, using your tracker's
native API/tools.

**Every comment posted to the tracker during triage must start with this disclaimer:**

```
> *This was generated by AI during triage.*
```

## Roles → your tracker

**Category roles** — map to your tracker's existing kind labels if you have them
(e.g. `Bug` / `Improvement` / `Feature`); create them only if absent.

**State roles → labels** (create if absent, once, deliberately):

| Role | Meaning |
|---|---|
| `needs-triage` | maintainer needs to evaluate |
| `needs-info` | waiting on reporter for more information |
| `ready-for-agent` | fully specified; an agent can start |
| `ready-for-human` | needs human implementation |
| `wontfix` | will not be actioned |

A triaged issue carries exactly one category + one state role. If they conflict, flag it and ask
the maintainer before doing anything else.

**Human-approval gate (do not forget):** if your pipeline auto-runs issues only when a human
created/authorized them, an agent-authored brief will NOT auto-run — after `ready-for-agent`,
tell the maintainer they must touch the issue to start it. Never work around the gate.

**PR surface (optional):** if PRs live on a git host (GitHub/GitLab), read them via that host's
CLI when a PR must be triaged — that is an add-on, not the core of triage.

## Reference docs (from upstream — read from the installed plugin path; if a file is missing, say so and stop, do not guess)

- `AGENT-BRIEF.md` — how to write durable agent briefs
- `OUT-OF-SCOPE.md` — how the `.out-of-scope/` knowledge base works

## Invocation

The maintainer invokes `/sdlc-triage` and describes what they want: "show me anything that needs
my attention", "look at issue 42", "move 42 to ready-for-agent", "what's ready for agents?".

## Show what needs attention

Query the tracker and present three buckets, oldest first: (1) never triaged (no pipeline
labels), (2) `needs-triage`, (3) `needs-info` with reporter activity since the last triage notes.
Counts + one line per item; let the maintainer pick.

## Triage one issue

1. **Gather context** — read the full issue (body, comments, labels, dates); parse prior triage
   notes so you don't re-ask resolved questions; explore the codebase with the project's domain
   glossary. Two checks: (a) **redundancy** — search for an existing implementation of the
   requested behaviour by domain concept (not just the request's wording) and report where you
   looked; (b) **prior rejection** — read `.out-of-scope/*.md` if present.
2. **Recommend** — category + state with reasoning + a brief relevant codebase summary. Wait for
   direction.
3. **Verify the claim** — for a bug, reproduce it from the reporter's steps (wrap commands for
   remote machines); report confirmed (with code path) / failed / insufficient detail (a strong
   `needs-info` signal).
4. **Grill if needed** — run your grilling skill (e.g. mattpocock `grilling`) with the maintainer
   live; an agent never stands in for the human side of a grilling session.
5. **Apply the outcome** per the roles table: `ready-for-agent` gets an agent-brief comment
   (AGENT-BRIEF.md format); `needs-info` gets triage notes ("What we've established" + "What we
   still need" — questions must be specific and actionable); `wontfix` gets closed —
   **already implemented** = point to where it lives (no `.out-of-scope/` entry),
   **rejected enhancement** = write `.out-of-scope/` note + link, **rejected bug** = polite
   explanation + close.

## Quick state override

If the maintainer says "move 42 to ready-for-agent", trust them: confirm what you're about to do
(labels, comment, state), then act. Skip grilling; if no brief exists, ask whether to write one.

## Resuming

If prior triage notes exist, read them first, check whether outstanding questions got answered,
and present the updated picture before continuing. Never re-ask resolved questions.
